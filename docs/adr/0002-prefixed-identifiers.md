# 2. Prefixed identifiers

Date: 2026-09-18

## Status

Accepted

## Context

Identifiers in a quality and compliance system are long-lived and widely handled. They appear in audit history, exported records, support tickets, and URLs, often separated from the query that produced them. An opaque identifier gives a reader nothing, and an identifier pasted into the wrong endpoint resolves to nothing rather than announcing the mistake.

[ADR 0001](0001-drizzle-orm-and-better-auth.md) settled on text primary keys generated by the application. This decides what goes in them.

## Decision

Every primary key Quality Runtime generates is `<prefix>_<random>`, for example `usr_v1stgxr8z5jdhi6b`. This governs row identifiers, not human-facing document numbers, standard clause references, or identifiers minted by other systems.

The prefix identifies the record type, so an identifier is self-describing wherever it turns up. Naming the _type_ rather than the table keeps the identifier format independent of physical table naming — `twoFactor` records carry `tfa_` and live in `two_factor`.

The random part is [Nano ID](https://github.com/ai/nanoid) over lowercase base36 (`0-9a-z`). Nano ID's own default is a 64-character URL-safe alphabet including `-` and `_`; both are dropped so the first underscore is unambiguously the prefix separator.

Case is dropped as well. These identifiers are read aloud on support calls, retyped out of exported records, and compared by eye in audit history, and a single case rule makes all of that safe: nothing downstream can lose a row by normalizing case, and the CHECK constraints reject a mixed-case identifier outright. Mixed case would add about 12 bits per 16 characters, which is a micro-optimization on top of an amount already far past sufficient.

A **row identifier is not a credential**, and length follows what an identifier does rather than how many rows a table holds:

| Length | Tables          | Why                                                           |
| ------ | --------------- | ------------------------------------------------------------- |
| 16     | everything else | An ordinary primary key                                       |
| 24     | `invitation`    | The identifier itself participates in a possession-based flow |

Sixteen base36 characters is about 83 bits (36^16 ≈ 8 × 10^24) — past any collision concern for a database identifier, and one rule covers almost the whole schema.

`invitation` is the exception because Better Auth takes an invitation _by id_ in `accept`, `reject`, and `get`. It treats a predictable invitation id as security-relevant, gating those calls on a verified email whenever ids are not its own opaque ones. Acceptance also checks the invitation's email against the session's, so the id alone is not a bearer token — but it is the one identifier here that is worth guessing, so it gets the wider size.

Sizing by table cardinality — wider for `session` and `verification`, narrower for `organization` — was considered and rejected. It is the wrong axis: `session.token` authenticates a session and `verification.value` proves a verification, so widening those `id` columns hardens nothing, and narrowing `organization` buys four characters in exchange for a third rule and a CHECK constraint that is painful to widen later.

`packages/db/id.ts` owns the prefix and length of every table and is the single place where identifiers are generated. Two things consume it:

- Each Drizzle `id` column defaults to `createId(type)`, so ordinary inserts need not think about it.
- `generateId` is shaped for Better Auth's `advanced.database.generateId`, which is how the library is told to generate these instead of its own.

Each table carries a CHECK constraint on the format:

```sql
CONSTRAINT "user_id_format" CHECK ("id" ~ '^usr_[0-9a-z]{16}$')
```

## Consequences

The format is enforced by the database, not by convention. A writer that has not been wired to `id.ts` — most importantly a Better Auth configuration that forgets `generateId` — fails on its first insert instead of quietly storing identifiers in a second format that later has to be migrated. `migrations.test.ts` applies the migrations to PostgreSQL and asserts exactly that rejection.

Adding a table means choosing its prefix and its length. `auth.test.ts` fails when Better Auth writes a table that `idFormats` does not cover, and `generateId` throws rather than inventing a format.

Changing a table's alphabet or length is a migration, because the CHECK constraints encode both. This is the intended cost: it makes the identifier format part of the schema rather than a convention that drifts. It also means a length should be chosen with room to be wrong in the safe direction — widening later is cheap, narrowing invalidates existing rows.

Passing a custom `generateId` changes one Better Auth default: because the function is not its own generator, `requireEmailVerificationOnInvitation` defaults to on, so accepting an invitation by id requires a verified email. That is a safe default and is left as it stands — the heuristic assumes custom ids may be predictable, which these are not, so a deployment that wants the plain emailed-invitation flow can set the option to `false` deliberately.

PostgreSQL text comparison is case-sensitive, but the alphabet is not, so lowercasing an identifier anywhere in the stack is a no-op rather than a lost row.
